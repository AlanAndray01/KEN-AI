# Code and API routing audit — 2026-09-30

This review inspected the application source, local configuration with secrets masked, and the configured database's global provider IDs, types, enabled flags, and base URLs. Database access was read-only. No user credentials or conversations were queried. Application code, credentials, and database records were not changed.

## What API is currently configured?

The local client calls `http://localhost:5000/api` (Express). The local server has Groq, Gemini, Cloudflare Workers AI, and Cloudflare AI Gateway credentials configured. Image generation explicitly selects Cloudflare. Mock AI is disabled.

The database inspection confirmed these global routes:

| Operation | Route implied by inspected configuration and code |
| --- | --- |
| Groq text | Direct `api.groq.com/openai/v1`; stored URL overrides Gateway |
| Gemini text | Direct `generativelanguage.googleapis.com/v1beta/openai`; stored URL overrides Gateway |
| Cloudflare chat | Cloudflare AI Gateway's Workers AI route, because no stored base URL overrides it |
| Cloudflare images | Cloudflare AI Gateway's Workers AI run route |
| Gemini images/PDF input | Separate native Gemini path; affected by finding 3 |
| Auto chat | Prefers available Groq models; Cloudflare is later in the preference list |

No independently deployed custom Worker URL was present in the inspected local environment or global provider records. Cloudflare Workers AI, Cloudflare AI Gateway, and a separately deployed custom Worker are different things. Per-user URL overrides and separately deployed production configuration were not inspected, and live provider requests were not made.

## Confirmed findings

### 1. Critical: credential testing can disclose a platform API key

Evidence: `server/src/services/ai/providerService.ts:219`, `server/src/routes/me.ts:26`, `server/src/services/ai/providers/OpenAICompatibleProvider.ts:92`.

The ordinary authenticated user's credential-test endpoint accepts a caller-supplied `baseUrl`. When `apiKey` is omitted, `testUserCredential()` falls back to the resolved platform credential and sends it in the Authorization header to that supplied URL. URL syntax validation does not bind the destination to the owner of the key. This also permits server-side requests to arbitrary destinations.

The offline reproduction captured a fake platform key sent to an `.invalid` destination using a mocked fetch. No real credential was transmitted.

Fix direction: never combine a platform key with a user-selected destination. Require the user's own key for arbitrary custom URLs, retain trusted platform endpoints for shared keys, and enforce destination/redirect policy against internal-network requests.

### 2. High: startup defeats the AI Gateway setting for seeded providers

Evidence: `server/src/services/ai/bootstrap.ts:33`, `server/src/services/ai/credentials.ts:227`.

Bootstrap saves each built-in vendor's default URL into the database. Credential resolution treats any stored URL as an intentional override and prioritizes it over `gatewayBaseUrl()`. Consequently, merely enabling the Gateway does not route those providers through it. The actual global Groq and Gemini records contain these vendor URLs.

Fix direction: distinguish seeded defaults from deliberate overrides; migrate existing default URLs without overwriting real custom endpoints. Resolve every request through one explicit routing policy.

### 3. High: Gemini image/PDF requests ignore the custom endpoint

Evidence: `server/src/services/ai/providers/GeminiProvider.ts:52`, `server/src/services/ai/AIProviderManager.ts:545`, `server/src/services/ai/providers/geminiNative.ts`.

`nativeAuth()` uses the global Gemini Gateway address instead of the adapter's configured base URL. However, the manager attaches the Gateway token only when the originally resolved text base URL points at the Gateway. With the inspected stored Google URL, native requests can therefore target the Gateway without Gateway authentication. On Gateway 401/403/404, the implementation retries Google directly.

A custom Worker selected for Gemini text will also be bypassed for inline images/PDFs. The offline reproduction confirmed the changed destination and missing header. Actual Gateway rejection was not probed.

Fix direction: explicitly configure native and compatible endpoints together, derive auth from the final destination, and make direct-vendor fallback an explicit policy when Worker-only routing is intended.

### 4. Medium: “Test connection” omits Gateway authentication

Evidence: `server/src/services/ai/providerService.ts:186` and `:225`.

Both admin and user test paths construct adapters with only `apiKey` and `baseUrl`. They omit `gatewayToken`, although normal manager-created adapters support it. A correctly configured authenticated Gateway can therefore appear to have invalid credentials in settings. The fake request reproduction confirmed the missing header.

Fix direction: share endpoint/auth construction between actual generation and credential probes. Keep the platform-key destination restriction in finding 1.

### 5. Medium: restart re-enables disabled Gemini models

Evidence: `server/src/services/ai/bootstrap.ts:55–62`, called from `server/src/server.ts` on startup.

For existing built-in Gemini models, bootstrap writes `enabled: true` along with catalog metadata. An administrator's disabled model can therefore become available again after restart. Existing model names/descriptions are also overwritten. The offline reproduction confirmed this update.

Fix direction: set initial enabled state only on insertion; preserve admin choices during catalog refresh.

### 6. Medium: data analysis has no completion/result path

Evidence: `server/src/services/analysis/ExternalAnalysisRunner.ts:35–75`, `server/src/services/tools/ToolManager.ts:172`.

Submission stores a process-local `queued` job, posts to the runner, and discards the successful response. `get()` only reads the same local map; it does not poll the runner. There is no completion update path in this implementation. Completed output remains unavailable, restart loses jobs, and the map has no expiry. Chat's data-analysis branch also discards the returned job instead of feeding its result into the reply.

The offline runner returned a completed result, but the application still returned `queued`. The feature is currently unconfigured locally, so this becomes a user-facing problem when enabled.

Fix direction: persist runner job IDs/status, implement polling or authenticated callbacks, and return results to the chat. Keep the feature unavailable until that flow exists.

## Features to simplify or leave disabled

- **Web search:** no local search provider/key; currently unavailable, not inherently useless. Hide or clearly mark it until configured.
- **Server voice:** no local voice provider/key. Browser speech fallback exists, so voice as a whole should not be called broken or removed automatically.
- **Data analysis:** incomplete as described above; leave disabled until completion handling works.
- **Legacy Anthropic provider:** the live global provider collection contains an enabled `anthropic` row, but the current adapter factory has no dedicated Anthropic implementation. Treat it as migration cleanup; do not expose it as supported without implementing the correct protocol. No key availability or live request was checked for this row.
- **Multi-Agents workspace:** development automation using the Claude Agent SDK, separate from the deployed chat provider flow. Optional if you do not use those commands. Root `test`, `lint`, `typecheck`, and `build` do not validate this workspace.
- **Large provider/model menus:** if this product should use only one custom Worker, unused provider configuration adds maintenance and UI complexity. Keep only deliberately supported choices visible; adapter interfaces themselves remain useful.
- **Routing documentation:** `docs/REQUEST_ROUTING.md` says pinned chat can fail over on quota, while the manager documents `fallbackPolicy: "none"` for pinned turns. Its “Flux only” image description also omits the current image fallback chain. Refresh these claims alongside routing changes.

## Making future custom Worker changes manageable

The existing `AIProviderManager` and adapter factory already provide a useful integration boundary. Extend that boundary rather than replacing the chat UI:

1. Register a dedicated custom provider with the actual Worker base URL, its auth contract, model IDs, and capabilities.
2. Centralize destination selection and auth for generation, streaming, testing, titles, native attachments, and image generation. A chat base URL currently does not control every one of these paths.
3. Make Worker-only routing explicit. Auto preferences, attachment routing, image fallback, and title generation can otherwise select other providers.
4. Preserve configuration overrides through startup and migrations.
5. Add regression tests for destination selection, credential isolation, SSE streaming, errors/timeouts, and model-disable persistence. Use fake credentials and mocked HTTP for these tests.

Do not blindly replace every vendor URL with the Worker URL: compatible chat, native Gemini media, and image generation use different endpoint shapes. The Worker's supported protocol determines the adapter work required.
