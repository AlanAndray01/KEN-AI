1. EXECUTIVE SUMMARY
================================================================================

Ken AI is a production-grade, full-stack AI chat platform built on the MERN
stack with TypeScript throughout (React + Vite on the frontend, Express on the
backend, MongoDB via Mongoose for persistence, and a shared types/schema
package binding the two together). It is deployed live at ken-ai.tech, with
the frontend on Vercel and the backend on Render.

The project began as a scaffolding exercise (Phase 1), grew a real database
layer (Phase 2), and then became a genuinely complete product in a single
large push (Phase 3) that added authentication, multi-provider AI chat with
streaming responses, account settings, and admin capabilities. From there the
work has been iterative hardening and polish: fixing real bugs surfaced by
actual usage, tuning security parameters for a memory-constrained production
server, deploying to real infrastructure with a custom domain, building out
a from-scratch autonomous multi-agent developer system, and — most recently —
a full brand and landing-page rebuild that went through several rounds of
revision before settling on its current form.

As of today, Ken AI supports eight AI provider integrations (Gemini, Groq,
OpenAI, Anthropic, OpenRouter, Cerebras, DeepSeek, Cloudflare Workers AI, and
local Ollama), mid-conversation model switching, streaming chat via
Server-Sent Events, web search and image generation tools, voice input/output,
cross-conversation memory, file attachments, conversation sharing and export,
user-defined custom GPTs, and a dark-mode-only design system built around a
distinctive black-and-neon-green "KEN" brand identity with a fully animated,
WebGL-powered marketing landing page.

The codebase is disciplined: it runs under strict TypeScript compiler flags,
has committed architecture rules that forbid faked features and hardcoded
secrets, and is covered by real automated test suites (Vitest across all
three workspaces) that are run as a hard gate before any change is considered
finished.

2. WHAT KEN AI IS
================================================================================

Ken AI is positioned as a general-purpose AI assistant and workspace — not a
narrow tool tied to one subject or one exam syllabus. A standing product rule,
established explicitly during development, is that Ken must behave like a
universal assistant capable of explaining any topic simply and with examples,
matching the answer quality of a frontier assistant, and never boxing itself
into being "just a homework helper" or "just a tutor for exam X."

The product identity, as configured in the system prompt layer, is:
"Ken AI, provided by Groq" — the assistant is instructed to identify itself
this way and never claim to be ChatGPT or attribute itself to a different
lab, regardless of which underlying model provider is actually serving a
given response (Groq, Gemini, Anthropic, OpenAI, etc. are all swappable
behind the same "Ken" identity).

The brand tagline, carried through the landing page, hero section, and
footer, is:

    "Intelligence without the noise."

The visual identity is a stark black-and-neon-green aesthetic: pure black
(#121212) canvas, off-white "smoke" (#F5F5F5) text, and a saturated brand
green (#00FF41) used exclusively as an accent for interactive elements,
glows, and emphasis. There is deliberately no light theme — more on why in
section 5.14.

3. TECHNOLOGY STACK
================================================================================

MONOREPO
  - npm workspaces: shared/, server/, client/, Multi-Agents/
  - Root package name: "Ken" (the repository has been referred to as
    "aether" in earlier scaffolding and "MERN Express Test" as the folder
    name; all three refer to the same single project)
  - Node.js >= 20 required

FRONTEND (client/)
  - React 19.1
  - Vite 7 (build tool and dev server)
  - TypeScript 5.9, strict mode
  - Tailwind CSS v4 (via @tailwindcss/vite, using the new @import
    "tailwindcss" / @theme inline syntax rather than a tailwind.config.js)
  - TanStack Query 5 for server state / data fetching
  - Zustand 5 for local client state (theme, drafts, model selection, UI)
  - React Router 7
  - react-markdown + remark-gfm + remark-math + rehype-katex + rehype-highlight
    for rendering assistant responses (GitHub-flavoured markdown, LaTeX math,
    and syntax-highlighted code blocks)
  - KaTeX for math rendering
  - highlight.js for code syntax highlighting
  - lucide-react for iconography
  - Zod for client-side schema validation
  - Vitest + @testing-library/react + jsdom for unit/component tests
  - Playwright for end-to-end tests (client/e2e)

BACKEND (server/)
  - Express 4.21
  - TypeScript, ESM modules (NodeNext resolution, ".js" import extensions
    even in .ts source — a deliberate ESM convention)
  - Mongoose 9 / MongoDB Atlas for persistence
  - argon2 (argon2id) for password hashing
  - jose for JWT handling
  - google-auth-library for Google OAuth
  - helmet for HTTP security headers
  - cors, cookie-parser
  - multer for file upload handling
  - pino / pino-http for structured logging
  - resend for transactional email (verification, password reset)
  - undici as the HTTP client for outbound AI provider calls
  - Zod for request/response schema validation
  - Vitest + supertest + mongodb-memory-server for backend tests (the test
    suite spins up a real in-memory MongoDB rather than mocking the database
    layer)

SHARED (shared/)
  - Published internally as @Ken/shared
  - Central home for TypeScript types, Zod schemas, and constants shared
    between client and server: CLIENT_ROUTES, model IDs, capability enums,
    the reasoning-tag stripping utility, and more
  - Built independently and consumed by both client and server as a
    workspace dependency

MULTI-AGENTS (Multi-Agents/)
  - Built on @anthropic-ai/claude-agent-sdk
  - A standalone, runnable autonomous agent swarm used for auditing and
    verifying the Ken AI codebase itself (see section 5.4)

STRICT TYPESCRIPT CONFIGURATION (applies across the monorepo)
  - noUncheckedIndexedAccess
  - exactOptionalPropertyTypes
  - verbatimModuleSyntax
  - isolatedModules

DEPLOYMENT
  - Frontend: Vercel
  - Backend: Render (free tier, 0.1 CPU / 512MB — a real constraint that
    shaped several engineering decisions, see sections 5.10 and 5.8)
  - Domain: ken-ai.tech, purchased and configured through name.com DNS
  - Email: Resend
  - Uptime: a cron-job.org keep-alive ping every 10 minutes, to prevent the
    free Render instance from cold-sleeping

5.4  THE MULTI-AGENT SYSTEM (Multi-Agents/)
--------------------------------------------------------------------------------

Separately from the Ken AI product itself, a standalone autonomous agent
system was built inside the monorepo as its own workspace, using
@anthropic-ai/claude-agent-sdk. The initial request came with a broken
sample file that called the SDK's query() function as though it returned a
Promise (`await query({ prompt })`); in reality query() returns an
AsyncGenerator of SDKMessage objects and must be consumed with
`for await (const message of query({ prompt, options }))`. This was
corrected and a complete, working system was built around it:

  Files: src/config.ts, src/types.ts, src/logger.ts, src/project-context.ts,
  src/agents.ts, src/guards.ts, src/runner.ts, src/missions.ts,
  src/planner.ts, src/verify.ts, src/report.ts, src/orchestrator.ts,
  src/cli.ts, run-agents.ts, plus a README.

The system was registered as a proper npm workspace with root-level scripts:

    npm run agents            — run the agent swarm
    npm run agents:audit      — run an audit mission
    npm run agents:verify     — run a verification mission

This system exists to let an autonomous agent swarm audit and verify the
Ken AI codebase itself — a meta-layer of tooling separate from the product
being built. It should not be confused with the "Ken-Orchestrator" persona
described in the next section, which is a presentation structure for
Claude's own replies in conversation, not a piece of runnable software.

--------------------------------------------------------------------------------
5.5  THE KEN-ORCHESTRATOR PERSONA
--------------------------------------------------------------------------------

Early in the project, a standing rule was established governing how Claude
should communicate throughout all future work on Ken AI, under the name
"Ken-Orchestrator": a senior AI technical director managing a multi-agent
MERN stack team. The rules, stated in absolute terms:

  1. Never dump long walls of text — break responses into clean,
     incremental, logical blocks.
  2. Follow a strict three-step pipeline when executing a task:
       STEP 1 (Planner)    — break the request into at most three micro-tasks
       STEP 2 (Specialist) — assign each to a named role (Backend, Frontend,
                              Security, or QA)
       STEP 3 (Executor)   — produce the exact production-ready code or
                              diagnostic steps, with zero fluff
  3. When a request is ambiguous, ask exactly one clarifying question before
     writing any code — never a list of questions.
  4. Prioritise code safety, proper error handling, and clean modular
     structure consistent with the project's own committed conventions
     (the .cursor/rules/ files).

This persona has governed the tone and structure of ongoing work in the
project ever since it was defined.

--------------------------------------------------------------------------------
5.6  EARLY BUG FIXES — REASONING LEAKAGE, FAKE THINKING UI, MARKDOWN TABLES
--------------------------------------------------------------------------------

Once Phase 3 was live and being used, real usage surfaced real bugs:

  REASONING TAG LEAKAGE
  Some reasoning models (e.g. Groq's GPT-OSS family) emit their internal
  chain-of-thought wrapped in <think>...</think> tags before the actual
  answer. These tags were leaking into the visible chat UI as raw text —
  the user explicitly rejected this ("I dont Want this Thing okay") and
  asked for the clean, invisible-reasoning streaming behaviour comparable
  to a mainstream assistant's UI.

  Fix: a boundary-safe reasoning filter was built in
  shared/src/utils/reasoning.ts. This was non-trivial because the SSE
  stream delivers content in arbitrary chunks — an opening or closing
  <think> tag can straddle two separate network frames, so a naive
  string-replace on each chunk independently would miss or mangle tags
  that split across a chunk boundary. The filter maintains state across
  chunks (createReasoningFilter(), with push()/flush()/isUnterminated())
  so it can correctly detect and strip a tag even when it is split.

  FAKE "THINKING" INDICATOR
  A follow-up product decision: rather than fabricating a fake "Thinking..."
  status message, the UI should show a real, minimal, dots-only streaming
  indicator with no extra text next to it — see section 5.7 for the
  finalized rule.

  MANGLED MARKDOWN TABLES
  Screenshots showed chat responses rendering tables incorrectly. This was
  diagnosed empirically rather than guessed at: the rendered textContent
  was compared directly against the screenshot and found to match exactly,
  proving the bug was a genuine rendering/parsing defect in the markdown
  pipeline rather than a display artifact, and it was fixed in the
  markdown rendering chain (react-markdown / remark-gfm configuration).

--------------------------------------------------------------------------------
5.7  LANGUAGE MATCHING AND THE DOTS-ONLY THINKING INDICATOR
--------------------------------------------------------------------------------

A pair of strict, explicitly-stated UI/behaviour rules were set for the
product:

  LANGUAGE MATCHING
  Ken must detect and reply in the same language the user writes in,
  rather than defaulting to English regardless of input language. This was
  implemented server-side as a dedicated LANGUAGE_RULE constant in
  server/src/services/chat/languageRule.ts, injected at the identity tier
  of the system prompt so it applies uniformly across every model provider.

  STREAMING THINKING ANIMATION
  While a response is being generated, the UI shows only a minimal dots
  animation — no additional text, label, or fake status message beside it.
  This directly followed from, and reinforced, the rejection of the fake
  "Thinking..." banner described in 5.6.

--------------------------------------------------------------------------------
5.8  PRODUCTION DEPLOYMENT — RENDER, VERCEL, DNS, DOMAIN
--------------------------------------------------------------------------------

This was one of the longest and most operationally involved phases of the
project, walking a non-infrastructure-background user through a real
production deployment step by step.

  BACKEND ON RENDER
  Initial deployment attempts failed with a 404 on the shared package
  (`@Ken%2fshared`). Root cause: the Render service's "Root Directory" had
  been set to `server`, but npm workspaces only resolve sibling workspace
  packages (@Ken/shared) when the build runs from the actual repository
  root. Fix: leave Root Directory blank so Render builds from the monorepo
  root, letting the workspace resolution work as intended.

  A second failure followed: TypeScript error TS2688, "Cannot find type
  definition file for 'node'". Root cause: Render's build ran `npm ci` with
  NODE_ENV=production set, which causes npm to skip devDependencies
  entirely — including @types/node, which the TypeScript compiler needs
  even for a production build. Fix: both render.yaml and vercel.json were
  updated to run `npm ci --include=dev` explicitly.

  Environment variables were configured iteratively, with the user
  repeatedly re-confirming values because Render's environment variable
  form does not autosave — a form UX trap that cost real time and was
  called out explicitly as something to double check every time.

  FRONTEND ON VERCEL
  Deployed separately from the backend, configured to call the Render API
  origin for all authenticated requests rather than relying on same-origin
  behaviour, since the two are on different domains.

  CUSTOM DOMAIN — ken-ai.tech
  Purchased through name.com and pointed at both the Vercel frontend and
  the Render backend (as an api subdomain) via DNS. This step surfaced a
  genuine mistake on Claude's part: querying api.ken-ai.tech before the DNS
  record actually existed caused a negative-cache entry on both Google's
  and Cloudflare's public DNS resolvers, which then continued returning
  NXDOMAIN for up to an hour after the record was correctly created,
  because those resolvers cache negative results too. This delayed the
  user by roughly an hour and was explicitly acknowledged as Claude's fault
  rather than attributed to name.com, Render, or DNS in general. A second,
  smaller mistake in this same phase was an early DNS-propagation-watcher
  script that reported a false positive by matching on the string
  "Address: 8.8.8.8" — which is simply the resolver's own IP echoed back
  in dig/nslookup output — rather than the server's actual A record.

  A REAL CODE BUG FOUND DURING DEPLOYMENT
  While debugging a broken-looking URL in production
  ("ken-ai.tech,https//www.ken-ai.tech/login"), the cause was traced to
  actual application code, not configuration: CLIENT_URL is stored as a
  comma-separated allow-list of origins, but it was being interpolated
  into redirect URLs as a single whole string rather than having the first
  entry selected. This was fixed in two places —
  server/src/services/auth/cookies.ts (a new clientOrigin() helper that
  splits on comma, trims, and strips a trailing slash) and
  shareService.ts — with five regression tests added to lock the fix in.

--------------------------------------------------------------------------------
5.9  LAUNCH READINESS — EMAIL, GOOGLE OAUTH, LEGAL PAGES, PERFORMANCE
--------------------------------------------------------------------------------

  TRANSACTIONAL EMAIL (RESEND)
  Configured for verification and password-reset email. A live bug —
  `emailSent: false` in responses — was traced not to a code defect but to
  the same Render environment-variable form UX issue from 5.8: the
  RESEND_API_KEY and RESEND_FROM_EMAIL values had visually appeared to be
  entered but were never actually saved, because the form silently
  discards unsaved changes if you navigate away. This tripped the user up
  three separate times before being conclusively identified. Separately, a
  ~7-10 second email delivery latency was investigated and explained.

  GOOGLE OAUTH
  A "deleted_client" error was traced to Render holding a stale/incorrect
  Google OAuth Client ID (the user had accidentally deleted and regenerated
  the real client in the Google Cloud Console, leaving Render pointed at
  a client ID that no longer existed). Separately, a missing COOKIE_DOMAIN
  environment variable was identified and added.

  A related Google "unverified app" branding warning was initially
  misdiagnosed — Claude first pointed the user toward the OAuth consent
  screen's "Data Access" tab, when the warning text explicitly said to
  visit the "Branding" page instead. The user pushed back directly on this
  ("why are you making it hard for me... find the cause and solution for
  it"), and the correct root cause was then identified: the OAuth consent
  screen was missing its required Privacy Policy and Terms of Service
  URLs. This was corrected, along with two smaller wrong claims made along
  the way — that the privacy/terms links were merely "optional" for saving
  the consent screen (they are not: publishing has stricter validation
  than saving a draft), and that the RESEND email configuration was
  "optional" in an environment-variable checklist (it is not: an
  unverified user cannot log in at all, since the login flow returns a
  hard 403 EMAIL_NOT_VERIFIED). Both incorrect claims were corrected and
  acknowledged directly when caught.

  PUBLIC LEGAL PAGES
  Commit: "Add public privacy policy and terms pages" — PrivacyPage.tsx,
  TermsPage.tsx, and LegalPage.tsx were added as real, reachable public
  routes (required both by Google's OAuth verification requirements and by
  ordinary product hygiene).

  A THIRD-PARTY ADVICE REVIEW
  At one point the user pasted deployment advice generated by a different
  AI tool. This was independently checked line by line rather than taken
  at face value, and four of the six suggested changes were found to be
  wrong for this specific setup: redirecting the Google OAuth callback to
  the raw onrender.com URL would have broken OAuth entirely; the suggested
  NODEMAILER_API_KEY / SendGrid variables named the wrong email provider
  (the project uses Resend); the note about vercel.app CORS was redundant
  since it was already handled correctly; and REACT_APP_API_URL was flagged
  as the wrong environment-variable naming convention for a Vite-based
  client (which uses the VITE_ prefix, not the Create-React-App prefix).

  PERFORMANCE TUNING
  A full pre-deployment test-and-performance pass was run across the whole
  project ahead of going live.

--------------------------------------------------------------------------------
5.10  SECURITY AND PERFORMANCE HARDENING (ARGON2ID)
--------------------------------------------------------------------------------

Commit: "Tune Argon2id for the 0.1-CPU instance"

Render's free tier allocates only 0.1 CPU and 512MB of RAM to the backend
service. The default Argon2id password-hashing parameters, while
appropriately conservative for a normal server, were measured to be
unnecessarily slow on this specific constrained instance. The parameters
were retuned:

    memoryCost:   19456
    timeCost:     2
    parallelism:  1

Benchmarked improvement: password hashing dropped from roughly 245ms to
71ms, and verification from roughly 289ms to 82ms. Critically, this change
is fully backward-compatible: Argon2's hash format encodes its own
parameters inline, so previously-hashed passwords created under the old,
slower settings continue to verify correctly with no migration required.

In the same conversation, the possibility of moving the backend to a
Pakistan-based host was discussed and guidance was given, though the
Argon2id tuning was treated as the higher-priority, lower-risk win and was
the change actually shipped.

--------------------------------------------------------------------------------
5.11  UNIVERSAL ASSISTANT REWRITE
--------------------------------------------------------------------------------

Commit: "Make Ken a universal assistant instead of an exam tutor"

A standing product-scope correction: Ken's system prompt and behaviour had
drifted toward acting like a narrow exam-preparation tutor. This was
rewritten so Ken behaves as a genuinely general-purpose assistant across any
subject, explains at whatever depth and simplicity the user's question
calls for, and is not implicitly scoped to any one curriculum, exam board,
or use case. This rule has been treated as a durable constraint on all
subsequent prompt and feature work — see the pinned memory
"ken-ai-response-quality-goal."

--------------------------------------------------------------------------------
5.12  EDITABLE MESSAGES
--------------------------------------------------------------------------------

Commit: "Make user messages editable and copyable"

Added the ability to edit a previously-sent user message and copy message
content directly from the chat UI. This feature's correctness was revisited
and repaired more thoroughly in the multi-agent fix round described in
section 5.16, after real usage surfaced a glitch where editing an earlier
message could leave a stray, incorrect final response appended at the
bottom of the thread instead of cleanly branching from the edit point.

--------------------------------------------------------------------------------
5.13  THE BRAND REDESIGN — LANDING PAGE AND DUAL THEME (FIRST PASS)
--------------------------------------------------------------------------------

The most recent and most extensive phase of work. The user supplied a
complete, self-contained HTML/CSS/JS landing page design (a large single
file with an inline <style> block and an inline <script> block implementing
letter-drop physics, a WebGL particle hero, a 3D animated robot, an
"intelligence core" visualization, a horizontal scroll-driven story section,
and several 2D canvas animations), along with logo SVG assets
(ken-mark.svg, ken-favicon.svg) and a colour palette reference image.

The initial request had three parts:
  1. Dual theme support — keep dark mode exactly as-is, and add a fully
     styled light mode matching the brand.
  2. A full chat-app UI redesign (chat interface, login, sign-up) to match
     the new landing page's futuristic aesthetic.
  3. Preserve all existing functionality (voice-to-text, tool selection,
     model switching) with zero regressions.

Work in this first pass included:
  - A full rebrand of client/src/index.css with new KEN palette tokens for
    both a light theme (--canvas: #ffffff, --accent: #00761f, etc.) and a
    dark theme (--canvas: #121212, --accent: #00ff41, etc.)
  - New Google Fonts: Lexend (body/display) and JetBrains Mono (code/mono)
  - A new KenMark.tsx logo component using useId() for gradient IDs so
    multiple simultaneous instances on a page do not collide, with the
    stem drawn in currentColor so it adapts to either theme automatically
  - A ~900-line landing.css authored specifically for the new page, with
    all custom properties prefixed --ln- to avoid colliding with the app's
    own design tokens, and documented light-mode-specific adaptations
    (deepened green for anything carrying meaning, since the raw neon

5.15  FIDELITY FIXES — MATCHING THE SUPPLIED DESIGN EXACTLY
--------------------------------------------------------------------------------

After the reversion in 5.14, the user sent the same supplied HTML file a
second time with the instruction to implement it "exactly as it is" with
"no adjustments." Rather than assume the existing port already matched,
the port was re-diffed against the actual supplied file, line by line, and
five genuine discrepancies were found and fixed:

  1. A STRUCTURAL BUG CAUSED BY THE SURROUNDING APP
     The supplied design is a standalone page authored against plain
     browser defaults, but it now had to render inside an app that uses
     Tailwind's global CSS preflight, which resets every element's margin
     to zero and forces replaced elements (like <svg>) to display: block.
     The supplied CSS relies on browser defaults for margins on several
     elements (.price, .usage, .status-pill, .story-num, .side-h, and the
     model spec <dl>) and relies on icons sitting inline with text. Under
     the app's preflight, all of that spacing had silently collapsed.
     Fixed by restoring the relevant defaults, scoped strictly inside the
     .landing class so nothing else in the app is affected.
  2. A missing .sec-wide utility class present in the source CSS but
     absent from the port.
  3. A missing shared font-family selector list applied to all the
     heading-like elements (h1-h5, .story-title, .final-h, .price, etc.)
  4. Missing -webkit-text-size-adjust and scroll-behavior: smooth on the
     scrolling root, which was why anchor-link navigation on the page was
     jumping instantly instead of gliding — restored scoped to this route
     only via an html:has(.landing) selector, so it does not affect
     smooth-scroll behaviour anywhere else in the app.
  5. A missing apple-touch-icon <link> that had been present in the
     original file's <head> but dropped from index.html.

count reported at each stage rather than assumed.

5.16  THE MULTI-AGENT FIX ROUND — THREE PARALLEL AGENTS
--------------------------------------------------------------------------------

With the landing page and dark-only theme in place, the user reported a

background agents (each instructed to run at high reasoning effort on the
Opus model), rather than being done directly — with the standing

Three tasks were defined and dispatched. Before dispatching, the file

same file at the same time — Task 1 (landing page) and Task 3 (chat
messaging logic) touch entirely separate files and were run concurrently;
Task 2 (chat visual restyle) was deliberately held back until Task 3
finished, since both would otherwise have raced to edit ChatPage.tsx.

  TASK 1 — LANDING PAGE RESPONSIVE AND VISUAL FIXES
  Scope: full 320px-width responsiveness with zero horizontal scrolling;
  fix a malfunctioning horizontal-scroll "story" section; remove random
  decorative lines that regenerated on every page load in the hero
  background; and remove the "Meet KEN" orbital diagram section entirely.

  This agent's background process stalled partway through (a stream
  watchdog killed it after 600 seconds of no progress, apparently
  confused by a second agent editing files concurrently), but its work had
  already been written to disk before the stall. Rather than trust its own
  incomplete final report, every claimed change was independently verified
  against the actual files:

    - Confirmed: the "Meet KEN" section was fully removed from the JSX,
      the animation hook, and the CSS (including its spin/spinBack/breathe
      keyframes, checked first for use elsewhere before deletion), and its
      test assertions were removed rather than left dangling.
    - Confirmed and diagnosed precisely: the horizontal story section's
      bug had two independent causes. First, .landing had
      overflow-x: hidden, which forces the browser to compute
      overflow-y: auto as well — silently turning the element into its own
      scroll container, which breaks every position: sticky descendant,
      since sticky elements resolve against their nearest scrolling
      ancestor rather than the viewport. This was the visible "one panel
      stuck with a large dead gap" bug. Second, the section's total
      scrollable height was a hardcoded 460vh while each panel was sized
      at 100vw (which itself double-counts the scrollbar width), so the
      scroll distance and the actual track width disagreed and the last
      panel never fully arrived. Fixed by changing overflow-x to clip
      (which still guards against overflow without creating a scroll
      container) and deriving the section's height directly from the
      actual panel count rather than a hardcoded value.
    - Confirmed: the random hero "neural constellation" lines (regenerated
      with Math.random() on every page load, matching the user's
      complaint precisely) were removed, while the separate, fixed,
      non-random floor/ceiling grid lines were correctly left in place, as
      instructed, since those are deterministic rather than the reported
      bug — flagged to the user as trivially removable on request.
    - Confirmed: a genuine 320px mobile pass was completed, including
      catching that the hero wordmark's own minimum clamp() size (78px)
      was itself too wide to fit a 320px viewport regardless of viewport
      scaling, and re-tracking it with a second, narrower clamp() below a
      400px breakpoint that meets the original clamp's floor exactly at
      400px, avoiding any visible jump between the two rules.

  All four gates (build, 0 typecheck errors, 0 lint errors, full landing
  test suite) were independently re-run and confirmed passing before this
  work was reported as complete.

  TASK 2 — CHAT VISUAL RESTYLE (SIDEBAR, MESSAGES, AUTH PAGES)
  Scope: restyle the chat interface, login/sign-up pages, and sidebar to
  match the landing page's exact colours, borders, fonts, and iconography,
  including matching the precise active-chat-item styling from the
  supplied design reference (green-tinted background, smoke-white text,
  and a 2px solid green left edge via an inset box-shadow).
  This task was deliberately sequenced to start only after Task 3
  completed, to avoid two agents fighting over the same file.

  TASK 3 — CHAT MESSAGING LOGIC (EDIT/REGENERATE BUG, ACTION TOOLBAR)
  Scope: two behavioural bugs — first, that not every assistant message in
  a conversation rendered its full action toolbar (Copy, Regenerate,
  Speak, Thumbs Up/Down), only some of them; second, that editing an
  earlier user message and resubmitting it would glitch, appending a
  single incorrect extra response at the bottom of the thread rather than
  cleanly truncating everything after the edit point and regenerating a
  fresh response sequence. This agent was explicitly instructed not to
  guess at root causes but to trace the actual code path — from
  UserMessageBubble's onEdit callback, through ChatPage's onEditMessage
  handler, through the truncateAfterEdit pure-function helper, through the
  optimistic UI update, to the eventual TanStack Query cache
  reconciliation — and to write regression tests proven to fail against
  the old, buggy behaviour before the fix, and pass afterward.

7. DESIGN SYSTEM
================================================================================

Ken AI runs a single, deliberately dark-only visual identity — there is no
light theme, and this is a firm product decision rather than an
unfinished feature (see 5.14). The reasoning: the brand's signature accent
colour, #00FF41, measures roughly 1.4:1 contrast against a white
background — well under any accessibility contrast floor and effectively
unreadable as text — so a "light mode" would require a materially
different accent colour, at which point it would no longer read as the
same brand at all.

STRICT TYPESCRIPT (enforced repo-wide)
  - noUncheckedIndexedAccess     — array/object index access is typed as
                                    possibly undefined, forcing explicit
                                    handling
  - exactOptionalPropertyTypes   — an optional property cannot be
                                    explicitly assigned undefined; it must
                                    be omitted entirely
  - verbatimModuleSyntax         — import/export statements are preserved
                                    exactly as written, distinguishing
                                    type-only imports explicitly
  - isolatedModules               — every file must be safely
                                    transpilable in isolation

CODE STYLE
  - Comments explain WHY, not WHAT — a comment referencing "the hidden
    constraint" or "the subtle invariant" behind a piece of code, not a
    restatement of what the code visibly does
  - No speculative abstraction, no unused feature flags, no
    backwards-compatibility shims for code that can simply be changed
    directly
  - Server code uses ESM with explicit ".js" import extensions even
    though the source files are ".ts", per the project's NodeNext module
    resolution setup

12. LESSONS LEARNED AND MISTAKES CORRECTED ALONG THE WAY
================================================================================

In the interest of a genuinely complete and honest record, this section
lists mistakes made during the project's development that were caught and
corrected — most of them Claude's own — rather than omitting them:

  1. Misreading the Claude Agent SDK's query() function as returning a
     Promise rather than an AsyncGenerator, in the very first request of
     the project (5.4).
  2. Querying api.ken-ai.tech before its DNS record existed, triggering a
     negative-cache entry on public resolvers that delayed the user by
     roughly an hour (5.8).
